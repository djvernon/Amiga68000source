Blit decode
-----------
BLTAPT: $AAAAAAAA & $55555555			Data for even bits

BLTBPT: ($AAA92A94 >> 15) & !($55555555) 	Data for odd bits

Minterm     ABC ABc AbC Abc aBC aBc abC abc
Input bits: 111 110 101 100 011 010 001 000
e4: 11100100
ABC + ABc + AbC + aBc = (ABC + AbC) + (ABc + aBc) = AC + Bc


Carrier Command Track Format.
-----------------------------
Track Gap - $AAAAAAAA longwords (1140 bytes total)

Track Start:-
	$AAAAAAAA

	$44894489 - two sync markers.

	Two longwords - MFM coded $FFFFFFTN
			(TN - track number)

	Data checksum - two longwords as MFM

	Actual data - 10240 bytes as MFM


SHO Track Format.
-----------------
Track Gap - $AAAAAAAA longwords (1140 bytes total)

Track Start:-
	$AAAAAAAA

	$44894489 - two sync markers.

(*)	$AAAAAAAA (Corrected to $2AAAAAAA - TODO check)

(*)	Eight unknown bytes (possibly with invalid clock bits)

(*)	$AAAAAAAA

(*)	$44894489 - two sync markers.

(*)	    $AAAA (Corrected to $2AAA - TODO check)

Start of data for blit decoding:-
(*)
5640 bytes of data for even bits	(First four bytes may always be $AAAAAAAA)
5640 bytes of data for odd bits

NB first four decoded bytes aren't output as sector data:-
 First word, $728ae, must be zero
 Second word, $728b0, is track number

(*) = Different from CC


Track 2 checksum $2ACEB281
Encrypted: $2A6E431B


For data #$00000002, code.longword gives:-
$AAAAAAA9	i.e. odd bits coded
$2AAAAAAA	i.e. even bits coded
This is the opposite way around to SHO.

blit.code.data currently also giving:-
$AAAAAAA9	i.e. odd bits coded
$2AAAAAAA	i.e. even bits coded

When width doubled to 8 bytes, output goes wrong after four bytes


odd: (2924a515 & 55555555) << 1
even: 514a4524

odd: (2a94a4a9 & 55555555) << 1
even: 49549154


The raw MFM data that must be presented to the disk controller will be twice as large as
the unencoded data. The following Table shows the relationship:
 1 ---> 01
 0 ---> 10 ;if following a 0
 0 ---> 00 ;if following a 1
